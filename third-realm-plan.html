1. End goal

The finished system has these properties:

  • Realm 3 is a real world process (AC_REALM_ID=3, own port, own character and world DBs) serving custom maps and custom DBC content.
  • Realms 1 and 2 continue to serve stock behaviour and content.
  • Every client that connects to realm 3 has a client data set that matches the server's data set exactly: DBCs, maps, vmaps, mmaps.
  • Client data is obtained and kept current by the launcher; the player does not manage MPQ files or patch order.
  • Adding a custom spell, item, or map is an additive data change recorded in a registry and produced by a build, not an edit to shipped binaries.
  • One build produces both the client artifact and the server artifact from the same inputs, under one content version.
  • Each artifact is content-addressed, verifiable and rollback-able.

The design problem is not “run a third world process” — that already exists in the form of realm 2. The problem is coexisting client data: the client loads one DBC/map set at process start, while realm 3 wants different data from realms 1 and 2.

2. Invariants that constrain the design

InvariantConsequence
A 3.3.5a client loads its DBCs and maps from Data/*.MPQ at process start. You cannot change the client's DBC set by switching in-game realms within one running client. Changing the set requires a relaunch.
A world process reads one DataDir tree. Each realm's server data is a directory. Different server data means a different mounted directory, not a runtime toggle.
The authserver advertises rows from acore_auth.realmlist; the client receives that list after login. A third realm is a row. Which clients see which rows is controlled by the auth process, not by the launcher.
The launcher is installed into the client directory and is the only reliable client-side writer/deliverer. Asset delivery is a launcher responsibility. It also inherits the Program Files write-permission problem already present for realmlist.wtf.
AC's DBC loader validates field count against its compiled struct and checks a few stock sentinel entries; it does not require a specific row count. Appending rows is compatible with the loader. Changing fields or removing stock rows is not.
Server data (maps/vmaps/mmaps/dbc) must be extracted from the same patched client data the players run. Client pack and server bundle must be generated together and share one version/hash lineage.
ac db-update targets auth, characters, world via the AC_*_DATABASE_INFO env vars. A custom world DB can reuse the normal db_world migrations by pointing the env at it. Multiple custom DBs need either repeated invocations with different env or an extension to the target list.

3. Data model: layers and append-only DBC

Treat all client/server data as layers. The layers define what may be shared, what is realm-specific, and what forces a relaunch.

LayerContentsMutabilityScope
L0 — stock Shipped 3.3.5a DBCs, maps, vmaps, mmaps, models, textures. Immutable. Treated as a checksum-verified baseline. All realms.
L1 — shared append New rows appended in reserved ID ranges: spells, items, maps, icons, visuals, map metadata. New model/texture/map files with new ids. Additive only. Never touches an L0 row. All realms. Idle where unreferenced.
L2 — realm overlay Replacements that cannot be expressed as appends: in-place edits of an existing map's ADT/WMO, or changed values for an existing ID that cannot be split. Replacement. Realm-specific. Only realms that opt in; requires pack switching and a relaunch.
append-only path derived / recorded
The invariant that makes realm 3 possible Realm 3's custom spells exist as new IDs in the shared DBC. Realms 1 and 2 load those rows too, but no item, trainer, quest, creature, or script on those realms references them. The client also never asks for them. They cost a few rows and nothing else.

4. Spell.dbc in detail

Spell.dbc is a fixed-record table. Appending a row means writing one complete, structurally valid record at the end of the file. The loader accepts it because the field count is unchanged.

4.1 How a custom spell is produced

  1. Choose an id in the reserved spell range (e.g. 500000+) that the registry marks free.
  2. Clone a stock row with the same shape as the desired effect; assign the new id.
  3. Change the fields that matter. Keep every reference (icon, visual, cast time, duration, range, radius) pointing at a row that exists in the same data set — reuse a stock row or append a new one.
  4. Write the row into the append source (CSV/JSON), not by hand into a binary.
  5. The build applies the row, packs the client MPQ, and extracts the server DBC from the same patched client.
  6. Realm 3 grants the spell through its world DB, a script, or a custom item. Realms 1 and 2 never grant it.

4.2 Differences that are not “new spells”

SituationAppend-only handling
Realm 3 needs a variant of a stock spell. Clone the stock row to a new id, modify the clone. Stock row untouched. The client shows the new spell only where realm 3 exposes it.
Realm 1 and realm 3 need different values for the same spell id. Two options: append two new ids and point each realm at its own; or keep the id and differ only server-side via a realm-id guard in SpellInfoCorrections.cpp. Client tooltips will show the DBC value, so if tooltips must differ, use separate ids.
Change is purely server-side (damage, coefficients, proc logic) and display can stay stock. Do not touch client DBC. Implement in SpellInfoCorrections.cpp or a spell script. Gate on realm id if realms differ. Client DBC remains L0.
A stock id must be redefined client-side per realm. Not expressible as an append. This is the L2 overlay case and forces pack switching for that realm.

4.3 Loader and validation notes

  • AC reads each DBC, checks its field count against the compiled struct, and checks a handful of sentinel entries for version sanity. Appended rows do not affect either check.
  • Localized tables have a base file and locale variants. A new row with a localized name needs entries written in both places or the client shows a missing/blank string for non-default locales.
  • Some tables are referenced by other appended rows. The build must validate the whole closure: new spell → icon → visual → cast time → duration → range, and so on.
  • Server and client DBCs must be identical for the realms that use the rows. Generating both from one build enforces this mechanically.

5. Map data in detail

NeedClient artifactServer artifactLayer
New map (new id) New ADT/WDT, WMO/M2, textures, Map.dbc, AreaTable.dbc, WorldMapArea.dbc, loading screen, light data as needed. maps/<id>_xx_yy.map, vmaps, mmaps, matching DBCs. L1
In-place edit of a stock map Replacement ADT/WMO for the existing map id. Re-extracted map/vmap/mmap for that id. L2
Spawns and objects on new maps Nothing. World DB rows referencing the new map id. DB

New maps are the clean case: they are additive and shareable exactly like appended spells. Editing a stock map is the one data class that genuinely cannot be shared between realms with different needs; it forces the overlay or isolated-edition options.

6. End-state options

Three distinct end states satisfy “third realm with custom assets”. They differ in how client data is distributed and how much per-realm divergence is possible. Each is described as a complete end state, not as a step toward another.

6A. Option A — shared append-only dataset

One client data set (L0 + L1) is installed for every player. One server data lineage serves all realms. Realm 3 differs only by which new IDs its DB and scripts reference, plus realm-gated server logic. One authserver advertises all three realms.

Properties

  • Client install: one data set; one download; no relaunch to switch.
  • Auth: one process, three realm rows.
  • Server data: one lineage; realm processes may still have separate DBs.
  • Custom content: new spells/items/maps by append; realm-gated behaviour in C++ for values that differ.
  • Not covered: in-place edits to stock maps/DBC rows that must differ per realm.

6B. Option B — base + per-edition overlays

A shared base (L0 + L1) is always installed. Realms that need conflicting replacements get an overlay pack (L2). The launcher selects the base plus the overlay for the chosen edition, and the edition is reached through its own logon endpoint so the client never sees a realm it cannot render.

Properties

  • Client install: base plus zero or more overlays, one active at a time.
  • Auth: possibly two logon endpoints (or one auth with a realm allowlist filter) so stock clients never see realm 3.
  • Server data: separate lineages, e.g. base and custom.
  • Custom content: full per-realm freedom, including stock-row replacement and in-place map edits, at the cost of pack switching and relaunch.

6C. Option C — isolated editions

The custom edition is a separate client installation with its own launcher, auth endpoint, worlds and data. Nothing is shared at the client level.

Properties

  • Client install: two full clients. Each edition patches independently.
  • Auth: separate auth processes. Accounts either duplicated or linked by a shared external identity.
  • Server data: fully separate.
  • Cost: duplicate downloads and disk, two launchers, two update streams.

8.3 Database topology

  • acore_auth is shared. Realm rows are the only per-realm auth-side data.
  • Each realm has its own character and world DB. Custom world DB starts from the normal base and applies the normal db_world migrations via AC_DB_UPDATE_ON_STARTUP or an explicit ac db-update with the custom env.
  • Custom world content (spawns, references to appended IDs) is a separate tracked SQL delta, applied after migrations. It is not merged into upstream migration files.
  • Realm 3 row: realmlist(id=3, name, address, port=8089, gamebuild=12340).
Updater limitation ac db-update resolves targets auth, characters, world and fixed db_* directories. Running it for a custom DB works by pointing AC_WORLD_DATABASE_INFO / AC_CHARACTER_DATABASE_INFO at the custom DBs. If several custom DBs must be updated in one command, add named targets to GetDatabaseUpdateTargets().

8.4 Logon isolation (Option B)

To keep a stock client from seeing realm 3, the realm advertisement is controlled at the auth process. Two implementations exist:

  • Two auth processes: each reads the same auth DB but advertises a subset. Requires a core filter (config/env) or separate views. Two IPs or hostnames on port 3724.
  • One auth process with an allowlist: patch RealmList::UpdateRealms / the auth session's realm-list packet building to filter rows by a configured set. The logon host determines the set.

Option A needs none of this because every client can render every realm.

9. Build and release pipeline

The build is the only place where client and server artifacts are allowed to diverge. It produces both from one input tree and one version.

9.1 Version coupling

VersionOwnerChecks
Core image revision revision.h / image tag Content manifest declares a minimum compatible core.
Content version Content repo tag / build id Client manifest and server manifest carry the same id and hashes.
DB migration head data/sql/updates Custom world DB reports the same head as the shipped migrations.
Launcher version MSI release Manifest declares min_launcher; older launchers refuse the pack.

9.2 Release and rollback

  1. Build produces artifacts and manifests into immutable, content-addressed storage.
  2. Server lineage is uploaded to content/<lineage>/<version> and verified against the manifest.
  3. The current symlink is flipped; the world process restarts and mounts the new version.
  4. Health verifies the running data version equals the published live version.
  5. Rollback flips current to the previous directory and restarts. Client manifests are versioned, so the launcher can follow or pin.

10. Launcher end state

The launcher becomes a content manager: it knows which files the active edition needs, keeps them verified, activates them into Data/, and only then writes realmlist.wtf and launches the game.

10.1 Manifest

{
  "schema": 1,
  "content_version": "2026.11.1",
  "min_launcher": "1.4.0",
  "min_core": "2026.11.1",
  "packs": {
    "base": {
      "dir": "base/2026.11.1",
      "files": [
        { "path": "Data/patch-4.MPQ", "size": 0, "sha256": "..." }
      ]
    },
    "custom-overlay": {
      "dir": "custom-overlay/2026.11.1",
      "files": [
        { "path": "Data/patch-5.MPQ", "size": 0, "sha256": "..." }
      ]
    }
  },
  "editions": {
    "stock":  { "logon": "logon.arenacraft.fun",  "packs": ["base"] },
    "custom": { "logon": "custom.arenacraft.fun", "packs": ["base", "custom-overlay"] }
  }
}

10.2 Activation model

  • Option A: one pack. Activation is a one-time hardlink/copy of the pack's patch-*.MPQ into Data/; no switching.
  • Option B: base is always active. The edition's overlay is linked in and any other managed overlay is removed. Requires the game to be closed. The launcher then writes the edition's logon host.
  • Option C: each launcher manages only its own full install; no cross-edition state.

10.3 Security and integrity

  • HTTPS through WinHTTP so the Windows trust store and proxy settings are used.
  • Content-addressed URLs: a file is fetched by sha256 and verified before activation.
  • Optional signed manifest (ed25519) with the public key embedded in the launcher; a compromised CDN cannot inject content.
  • Path validation on manifest entries, disk-space checks before download, atomic rename only after verification.

11. Maintenance invariants

These are the rules that keep the system from rotting. They apply regardless of the chosen option.

InvariantEnforcement
Stock rows are never modified. Build compares each L0 DBC against a stored checksum baseline; only appends are allowed.
Every new ID is unique and in its reserved range. id-ranges.json registry; CI collision check against stock and previously allocated IDs.
Every appended row has a valid reference closure. Build validates icons, visuals, cast times, durations, ranges, map metadata and locale rows.
Client and server DBCs match. Both are produced from the same patched client; build compares their hashes.
Every artifact is reproducible and identified. Content version + manifest hashes; no hand-edited binaries in git.
Realm-specific behaviour that cannot be appended is code, not data. Realm-id guards in SpellInfoCorrections.cpp or scripts; reviewed like any core change.
Custom world DB stays migration-compatible. Run normal db_world migrations, then the tracked custom SQL delta; verify the migration head.
Running server data matches the published live version. Health reads the mounted manifest and compares it to the live manifest.
Rollback is possible without a rebuild. Versioned directories plus the current symlink; previous client manifest retained.

11.1 Content repository layout

arenacraft-content/
  src/client/          # Noggit maps, models, textures
  src/dbc/             # append rows as CSV/JSON, grouped by table
  src/sql/world/       # custom world content delta
  id-ranges.json       # allocated ranges and owners

  build.manifest       # lineage -> packs -> realms

11.2 What stays in the core repo

  • Server-only rules and corrections (src/game/Spells/SpellInfoCorrections.cpp, spell scripts).
  • Infra module definitions and the realm row migration.
  • Launcher and content-client logic.
  • No binary content, no MPQs, no extracted maps.

12. Failure modes and conflict classes

ClassExampleHandling by option
Client pack older than server data Server has new appended spell; client lacks the row. A/B: launcher enforces content version before launch. C: same, per edition. Health/monitor reports mismatch.
Stock row edit Someone changes an existing Spell.dbc row. CI rejects it. If intentional and global, it becomes an explicit L2 or a baseline change with a new L0 checksum.
ID collision Two custom spells allocate 500001. Registry + CI rejects the build.
Broken reference New spell points at a missing icon. Build validation fails; no manifest is published.
In-place map edit needed per realm Realm 3 changes an existing arena's geometry. A: not possible per realm. B/C: overlay or isolated install.
Wrong overlay active Player launched custom after switching to stock without relaunch. B: launcher ties logon host and active pack; refuses on mismatch.
CDN compromise Malicious pack served. Signed manifest; sha256 per file; launcher refuses unsigned changes.
Program Files permissions Cannot write Data/ or realmlist.wtf. Launcher reports and refuses to launch against the wrong state.
Custom DB migration drift Custom world DB misses an upstream migration. Startup update or explicit update; health checks the migration head.
Locale string missing Appended row only in base DBC, not locale DBC. Build validates locale variants for localized tables.

13. Open decisions

  1. Which option is the target: A (shared append-only), B (base + overlays), or C (isolated editions)? The answer is determined by whether in-place stock edits or same-ID value changes must differ per realm.
  2. If B: separate auth process per edition, or one auth with a realm allowlist filter?
  3. Where do client artifacts live: object storage/CDN, or netcupbox nginx?
  4. Reserved ID ranges: initial allocation for spells, maps, items, icons, visuals.
  5. Content repo: dedicated repository, and who owns the Windows authoring step (Noggit/DBC tooling)?
  6. PTR: leave as realm 2, or repurpose as a staging lineage for custom content?
  7. Rollback policy: how many previous content versions are retained on the server and in the CDN?
